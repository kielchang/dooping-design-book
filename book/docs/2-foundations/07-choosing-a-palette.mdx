# 色票配色策略

**適用**：新增環境色主題、新增或重生分類色票、調整任何生成出來的色值時。
已定案的值見[色彩語意](/foundations/color)、[深淺主題](/foundations/theming)、[提醒色辭典](/foundations/alert-colors)；
圖表上每個系列取哪一種顏色，見[圖表的配色策略](/components/charts#配色策略先問資料形態再問維度語意)。

**不能靠目測，要靠驗證器。** 值由生成器產生，由 `npm run verify:color` 驗收。

## 三層：語意 → 色相預算 → 並存

配色分三層，由上而下套用：

| 層 | 規則 | 詳見 |
| --- | --- | --- |
| **1. 語意** | Token 名稱說「代表什麼」；語意色是唯一的色彩 API，色階不外露。狀態色語意固定，切主題、切深淺都不變 | [色彩語意](/foundations/color#四組語意職責不重疊)、[提醒色辭典](/foundations/alert-colors) |
| **2. 色相預算** | 主題色只進外殼（側欄＋頂列的 `--sidebar` 家族）；內容面、動作、互動、狀態色、圖表色都不跟主題走 | [深淺主題 → 色相預算](/foundations/theming#色相預算主題色只進外殼) |
| **3. 主題色與辨識色並存** | 分區：主題色只在外殼，按鈕、提醒、欄位只在內容面。飽和度：`--danger` 是畫面上最飽和的色，外殼的彩度低於它。面積：高飽和色（提醒關鍵色＋圖表重點色）共用 10% | [色彩語意 → 並存三層](/foundations/color#主題色與辨識色並存分區飽和度面積) |

分類色票（`--chart-1` … `--chart-8`）不進這三層：與狀態語意脫鉤、不跟主題走、不得靠近任何狀態色，
見[色彩語意 → 分類色票](/foundations/color#分類色票與狀態語意脫鉤)。

## 值是生成的，不是挑的

環境色（外殼）、內容面的中性色、提醒淡底、預設外殼、分類色票，以及未達標的狀態色前景，都由
`packages/tokens/scripts/generate-theme.mjs` 生成：**給定目標（對比比值或感知距離），反解明度與彩度**。

```bash
npm run build:theme    # 重新生成主題色、淡底、圖表色票（改寫 tokens.json）
npm run build:tokens   # 由 tokens.json 重產 tokens.css、tailwind.css、tokens.data.ts
npm run verify:color   # 閘門：有不合格項就 exit 1
```

| 生成的值 | 做法 | 參數 |
| --- | --- | --- |
| 環境主題的外殼（`--sidebar` 家族） | 依色階給定明度與彩度上限（深色模式彩度約打八折）；選中項同色相往亮探到與外殼 ΔE00 8、白字仍 ≥ 4.5:1；次要文字反解到 4.8:1；標誌塊與外殼反相 | `THEMES` 的 `hue`、`tier`；`SHELL`、`SHELL_ACCENT_MIN`、`SHELL_SECONDARY` |
| `--brand`／`--brand-foreground` | 鏡射 `--primary`（所有主題同值，只有預設主題宣告） | — |
| `--brand-subtle`／`-foreground` | 淺色從最淡往深探、深色從最深往亮探，取第一個與 `--muted`、預設外殼都拉開 ΔE00 8 的值；文字反解到 4.5:1 | `SUBTLE_MIN` |
| 14 個內容面中性色 | 轉到石墨的色相（265°），明度與彩度不動；`--muted-foreground` 對 `--muted` 反解到 4.5:1。只放在預設主題，其他主題沿 cascade 共用 | `NEUTRAL_TINT`、`CONTENT_HUE` |
| 狀態色前景 | 未達 4.5:1 才修：success／warning／info 改同色相深墨前景；danger／destructive 保留白字、壓深填色 | — |
| `--{狀態}-subtle`／`-foreground` | 四種共用一個明度，各色相彩度反解到同一個染色量；文字反解到 4.5:1 | `SUBTLE_TINT`、`SUBTLE_L_BAND` |
| 預設外殼 `--sidebar` | 反解到與頁面底的目標 ΔE00 | `SIDEBAR_TINT` |
| `--chart-1` … `--chart-8` | 從候選池以最遠點插入挑出（見〈排序：最遠點插入〉） | `CHART_BAND`、`CHART_CHROMA`、`HUE_SPACING`、`ANCHOR_HUE` |

一律取整成 8-bit 之後再驗，對**實際的前景與表面 token** 驗（見[色彩語意 → 對比要求](/foundations/color#對比要求)）。

<Rules>
  <Do><p>要改值就<strong>改生成器參數</strong>，重跑 <code>npm run build:theme</code>。</p></Do>
  <Dont><p>不要手改 <code>tokens.json</code> 裡生成出來的值。</p></Dont>
</Rules>

## 驗證門檻

所有門檻都對全部主題 × 淺深兩模式驗；守衛欄寫由誰擋。
`verify:color` 的不合格項同時讓 `npm test` 紅（`tests/color.test.ts` 跑同一組檢查）；warn 不擋，總數超過 15 則 `npm test` 紅。

| 選中項 `--sidebar-accent` 對外殼；選中項上的文字 | ΔE00 ≥ 8；≥ 4.5:1 | `verify:color` |

  <Dont><p>不要用色票研究時的比較底色驗完就收工。</p></Dont>
</Rules>

<Rules>
  <Do><p>驗證器的結果<strong>連同 warn 一起留下</strong>，並註明 warn 的補償措施

### 淺深各一組，各自驗

淺深各一組獨立的值，各自驗證。「每個模式各一份報告」**是覆蓋要求，不是格式要求。**

### 覆蓋範圍要逐字等於宣稱的保證

分類色不得撞語意狀態色；比對對象是**全部六個狀態色**，不是只比 `danger`。
**只驗一個對象，等於沒有驗那一類。**

### 驗感知量，不驗參數值

**驗證器要驗的是感知量，不是參數值。**
例：四個狀態淡底以**染色量**等量，不以彩度數值相等。

### 背景改版之後，驗證結果全部作廢

只要動過背景色（深色模式重做表面層次、卡片底色調亮一階），
**所有色票的驗證結果都必須重跑**：先 `npm run build:theme` 重新生成，再 `npm run verify:color`。

<Callout variant="warning" title="驗證結果旁邊記背景值">
  把<strong>驗證所用的背景值記在結果旁邊</strong>，並在背景 token 變更的檢查清單裡
  加一條「重跑色票驗證」。
</Callout>

## 門檻優先序

<Callout variant="info" title="門檻的優先序">
  <strong>無障礙門檻（對比、色覺障礙 ΔE00）不得為了美感放寬；
  擠不下去時放寬的是美感約束</strong>（明度帶、彩度上下限、色相間距）。
</Callout>

| 約束 | 項目 | 擠不下時 |
| --- | --- | --- |
| 無障礙門檻 | 對比 4.5:1／3:1、分類色兩兩 ΔE00 ≥ 10（含 protan／deutan） | **不放寬** |
| 美感約束 | 明度帶 `CHART_BAND`、彩度上下限 `CHART_CHROMA`、色相間距 `HUE_SPACING` | 先放寬這裡 |

加一條硬約束（例如「不得靠近狀態色」）的同時，放寬一條**美感約束**
（色相間距、明度帶上下限）。

**先過驗證，再談風格。**

## 排序：最遠點插入

分類色票的順序就是**安全順序**：

1. **第 1 色錨在藍**（`ANCHOR_HUE`）：候選池裡色相最接近錨點、明度最接近明度帶中點的那一個。
2. **之後每一色**：在與已選各色色相差 ≥ `HUE_SPACING` 的候選裡，取「與已選色的最小感知距離最大」的那一個。
   感知距離取一般、protan、deutan 三種視覺下 ΔE00 的最小值。
3. **取用端照序取** `--chart-1` … `--chart-k`，不重排、不循環。

候選池＝明度帶內 × 每 2° 一個色相，彩度落在上下限內、對頁面底 ≥ 3:1、且不靠近任何狀態色。
前 k 色的最差一對見[色彩語意 → 順序即安全順序](/foundations/color#順序即安全順序)。

<Rules>
  <Do><p><code>PALETTE[0]</code> 要<strong>穩定</strong>：它是單序列圖表沒指定顏色時的預設色。</p></Do>
  <Dont><p>不要用「取材來源的命名順序」或色相環順序當陣列順序。</p></Dont>
</Rules>

## 定案

定案＝只改 token 的值。換色票不動任何一行使用它的程式碼（見[色彩語意](/foundations/color)的命名）。

**例外：重新排序會打到寫死索引的畫面。**
寫成 `PALETTE[3]` 的地方，重排之後對應到的是不同色相。

<Rules>
  <Do><p>重排色票時，把<strong>所有寫死索引的位置列出來逐一目視</strong>，
  當成這次變更的驗收項目。</p></Do>
  <Dont><p>不要以為「反正只是換顏色」。</p></Dont>
</Rules>

定案前依序完成：

1. `npm run build:theme`，再 `npm run build:tokens`
2. `npm run verify:color` 全過；warn 連同補償措施記下
3. `npm test`
4. 候選組（含淘汰組）與驗證結果留在文件或 story 裡
5. token 值有變：依[版本策略](/governance/versioning)定 `@dooping/tokens` 的版號，CHANGELOG 寫一則

## 新增一組主題

環境主題只產生外殼。現有的 8 個色族（每族深淺兩階）已經把色輪排滿：
**加進既有色族**（例如某族只用了一階）優先；**新開色族**要先走[回饋與 RFC 流程](/governance/rfc)，
因為它得和兩側的色族都拉開 ΔE00 10。

1. **選色族與色階**：加進既有色族就沿用該族的 `hue`，換 `tier`；新色族選一個與相鄰色族都拉得開的色相。
2. **加參數**：在 `packages/tokens/scripts/generate-theme.mjs` 的 `THEMES` 加一筆（欄位見下表）。
3. **生成**：`npm run build:theme`，再 `npm run build:tokens`。
4. **驗收**：`npm run verify:color`。沒過或生成器丟錯（無解、拉不開），回第 1、2 步改參數重跑（見下表）。
5. **改測試**：`tests/color.test.ts` 的主題數與色票數斷言跟著改，跑 `npm test`。
6. **補文件**：[環境色票](/foundations/environment-palette)的色票清單加一列（`tests/environment-theme.test.ts` 會核對），
   色族是新的就在「色族的語意」補一列。Storybook 工具列與宿主的主題選單讀 tokens，不必另外登記。
7. **定案**：見〈定案〉。

`THEMES` 的欄位：

| 欄位 | 填什麼 |
| --- | --- |
| `name` | `data-color-theme` 的值 |
| `label` | 顯示名 |
| `family` | 色族鍵，用色名（`red`、`cyan`…），不用業務名稱 |
| `term` | 華語基本色名（＋修飾詞），例如「青」「黃褐」 |
| `tier` | `base`（淺階）、`deep`（深階）；`neutral` 是無色相的深色外殼，`default` 只給預設主題 |
| `hue` | OKLCH 色相；同族兩階用同一個 |

沒過時改哪個參數：

| `verify:color` 報的 | 改什麼 |
| --- | --- |
| 跨族外殼 ΔE00 不足 10 | 換 `hue`，離相鄰色族遠一點 |
| 同族兩階 ΔE00 不足 8 | 調 `SHELL` 兩階的明度差（會影響全部色族，改完要全部重驗） |
| 家族不連續 | `hue` 落進了別族的範圍；換 `hue` 或改 `family` |
| 環境外殼對頁面底不足 10（深色模式） | 提高該色階深色模式的明度；中性外殼沒有色相可拉開，只能靠明度 |
| 外殼文字或次要文字不足 4.5:1 | 降低該色階的明度 |

## 新增或擴充分類色票

### 新增：重生一組色票

**1. 一次做多組候選，並排比較。**
至少做 5–7 組，每組給一個**風格描述**（「沉穩企業感」「高飽和儀表板感」「柔和親和」），
用**同一份資料、同樣幾張圖、淺深兩色模式並列**呈現。

候選的來源可以是既有色票、品牌情緒板、公開的色票庫，但**沒有一組能直接拿來用**：
只取它們的**方向**（色相家族、飽和度層級），轉成生成參數
（`CHART_BAND` 明度帶、`CHART_CHROMA` 彩度上下限、`HUE_SPACING` 色相間距，淺深各一組）。

<Rules>
  <Do><p>把候選組與它們的驗證結果<strong>留在文件或 story 裡</strong>，
  包含<strong>被淘汰的那幾組</strong>。</p></Do>
  <Dont><p>不要只做一組然後開會表決。</p></Dont>
</Rules>

**2. 每組各跑一次** `npm run build:theme` → `npm run verify:color`，每組候選、每個模式各一份報告。
在自己的技術棧驗證時，報告至少要有這些：

```js
// 驗證器的輸出長這樣：每組候選、每個模式各一份
// { 亮度帶: pass, 彩度: pass, CVD分離: warn(ΔE 11.4 floor), 對比: pass }
//
// 三件事必須寫進報告，否則結果無法被重現：
//   1. 用哪個背景值驗的
//   2. ΔE 的地板值定在多少
//   3. 哪幾色只是「勉強過」（下次微調時第一個被動的就是它們）
for (const mode of ["light", "dark"]) {
  report[mode] = validate(palette[mode], { background: SURFACE[mode].bg, deltaEFloor: 10 });
}
```

**3. 沒過：改參數，不改值。** 依〈門檻優先序〉先放寬美感約束，無障礙門檻不動。

**4. 選定：先過驗證，再談風格。**

**5. 定案**：見〈定案〉；順序有變時，逐一目視寫死索引的畫面。

### 擴充：類別超過八個

1. **先合併**：尾端類別併成「其他」，明細放在別處（`capItems`）；
   跨圖表反覆出現的實體用 `colorByKey`，第 9 個以後退 `--muted`
   （見[圖表的配色策略](/components/charts#配色策略先問資料形態再問維度語意)）。
2. **仍要第 9 色**：新增 token 走 [RFC](/governance/rfc)。通過後生成器、`verify:color` 與 `PALETTE`
