# 情境化申請單

**適用**：主檔維護——取代攤開全部欄位、什麼都能改的大表單。

**先選情境，再填欄位。**

```
① 挑情境          ② 只顯示該情境的欄位      ③ 必填「異動原因」
   單位升等   →      等級、折扣率、信用額度  →   為什麼要升等
   暫停往來   →      狀態、生效日            →   為什麼暫停
   更新聯絡   →      聯絡人、電話、地址      →   （免填，非敏感）
                                            ↓
                                   一筆帶情境與原因的稽核記錄
```

- 情境定義「這件事要改哪些欄位」。
- 稽核記錄帶「為什麼」，不只有「改了什麼」。
- 權限可以掛在情境上（誰能做升等）。

## 寫進既有的稽核記錄

情境化申請單**直接寫進既有的稽核記錄**，多帶 `scenario` 與 `reason` 兩個欄位。

<Rules>
  <Do><p>申請單 → 立即套用 → 記一筆帶情境與原因的稽核。<strong>單一資料源。</strong></p></Do>
  <Dont><p>不要另建一套「申請單」資料表然後跟主檔對帳。</p></Dont>
</Rules>

## 不屬於任何情境的異動

不回頭開放全欄位編輯，而是：
- 保留一個「其他異動」情境（欄位較寬鬆，但**原因必填且要寫得具體**）
- 某個「其他」被用了 20 次，就補一個正式情境

## 規則

<Rules>
  <Do><p>情境數量控制在 <strong>6–10 個</strong>，每個都對應一件真實會發生的事。</p></Do>
  <Dont><p>不要為每個欄位各開一個情境（「改電話」「改地址」「改分機」）。</p></Dont>
</Rules>

## 實作

- 情境 → 欄位對映寫成設定（`Record<Scenario, FieldKey[]>`），不要寫成 40 個 if
- 原因欄位是 `required`，而且**不接受少於 5 個字**
- 敏感情境（改額度、改狀態）一律留痕；非敏感（改聯絡方式）可以免原因，
  但仍然要記稽核
