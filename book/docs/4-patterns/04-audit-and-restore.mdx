# 稽核與回復

**適用**：要追得到「誰、何時、改了什麼、為什麼」，並且要能改回去的資料異動。

## 做法

### 1. 結構化的 before / after

稽核記錄不是一行字串，是結構：

```ts
{
  action: "update",
  target: { kind: "customer", id: "U-1042" },
  scenario: "tier-upgrade",        // 情境（若走情境化申請單）
  reason: "年度累計量達標，依規則升等",
  before: { tier: "silver", creditLimit: 1_000_000 },
  after:  { tier: "gold",   creditLimit: 1_500_000 },
  restoreKind: "customer",          // 有這個才可回復
}
```

`before`/`after` 直接取自[變更摘要](/components/change-summary)用的同一份 `Change[]`。

### 2. 可回復 vs 不可回復，用資料本身判定

```
有 before/after ＋ restoreKind  →  可回復
沒有                            →  不可回復
```

| 操作類型 | 可回復？ |
| --- | --- |
| 逐欄更新 | ✅ |
| 整份清單更新（存整份快照） | ✅ |
| 新增 | ❌ |
| 刪除 | ❌ |
| 批次操作 | ❌ |
| 確認／解鎖 | ❌ |

<Rules>
  <Do><p>用<strong>資料結構</strong>判定能不能回復，讓 UI 自動決定要不要顯示「回復」鈕。</p></Do>
  <Dont><p>不要維護一份「哪些動作可回復」的硬編清單。</p></Dont>
</Rules>

### 3. 回復本身也要留痕

回復動作**另記一筆稽核**，並標註 `restoredFrom: <原記錄 id>`。

### 4. 回復也受鎖定守衛

已鎖定期間的資料不能被回復；[硬鎖定](/patterns/hard-lock)對回復沒有例外。

## 規則

<Rules>
  <Do><p>稽核記錄要能<strong>回答問題</strong>：誰、何時、改了哪個欄位、從什麼變成什麼、為什麼。</p></Do>
  <Dont><p>不要記「使用者 A 更新了資料」。</p></Dont>
</Rules>

## 實作

- before/after 可以只對**敏感實體**開啟。
- 稽核寫入做進**共用的更新函式**，不要靠每個 mutation 自己記得寫。
