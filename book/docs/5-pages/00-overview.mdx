# 頁面總覽

本章規範**一整頁怎麼組**：元件章管單一控制項怎麼用，模式章管一類操作怎麼運作，本章管兩者之間的單頁組成。
**同一種頁型，在每套系統長一樣。**

## 三層分工

| 層 | 管什麼 | 文件 |
| --- | --- | --- |
| 站台層 | 側邊欄分區、全域狀態列、深連結、單一出口 | [後台系統的資訊架構](/patterns/back-office-ia) |
| **單頁層** | 一頁之內的區塊順序、組成元件、行為規範 | **本章** |
| 區塊層 | 每個元件自身的用途、狀態、無障礙 | [元件章](/components) |

本章不收應用外殼：外殼**元件**在[元件章](/components/app-shell-sidebar)，路由與資料由宿主負責，
站台層的**規範**在上表那一頁；本章從「進到這一頁之後」開始管。

本章的組合 story 放在 `packages/react/src/pages/`：那個目錄**只放 story、不發任何 registry item**，
元件一律在元件章（守衛：`tests/boundary.test.ts`）。

## 五種頁型

| 頁型 | 回答的問題 | 主角元件 | 文件 |
| --- | --- | --- | --- |
| 清單頁 | 那一筆在哪？ | DataTable | [清單頁](/pages/list-page) |
| 明細頁 | 這一筆的全貌？ | EditableField ＋ TabPills | [明細頁](/pages/detail-page) |
| 表單頁 | 建立一筆新的 | Input 家族 ＋ Stepper | [表單頁](/pages/form-page) |
| 儀表板 | 整體狀況如何？ | Charts ＋ KPI 磚 | [儀表板](/pages/dashboard) |
| 設定頁 | 改變系統的行為 | Card 分區 ＋ Dialog | [設定頁](/pages/settings-page) |

選頁型先問這一頁**回答什麼問題**，不要先想版面。
一頁要同時回答兩個問題（又要清單又要總覽）時，通常該拆成兩頁。

登入頁不列為頁型（組成就是 Card ＋ Input ＋ Button）。

## 跨頁一致性守則

這六條各頁型通用（各頁型文件不重複），違反任一條即為走樣：

| # | 守則 |
| --- | --- |
| 1 | 頁面標題永遠在左上，一頁只有一個 h1 |
| 2 | 每頁至多一顆主要動作，位置固定（清單頁右上、表單頁右下） |
| 3 | 操作回饋的去向全站固定一種 |
| 4 | 錯誤緊貼發生處，頂部只做彙總 |
| 5 | 同一實體跨頁同色（分類色跟實體走；與 [Charts](/components/charts) 配色策略、[GraphCanvas](/components/graph-canvas) 同一條規則） |
| 6 | 同一個東西全站同一個名字（不要清單頁叫「項目」、明細頁叫「紀錄」） |

## 新專案：從頁面開始規劃

既有系統走[三階段](/governance/adoption)導入（先 token、新畫面用元件、按需查模式）。
**全新專案直接從頁型開始：**

<FlowPageFirstSteps />

1. **列出所有畫面，各標上頁型。** 標不出頁型的畫面，先回頭想它回答什麼問題。
2. **每頁抄骨架與最小安裝集。** 各頁型文件末尾的「取用」段，一條指令裝齊該頁型需要的元件；
   版面照「頁面解剖」的區塊順序排。
3. **照各頁 Rules 驗收。** 每頁型的行為規範就是驗收清單；
   對照組合 story 看「組出來應該長怎樣」。

裝之前的前置條件（`components.json`、`@/*` 別名、token 安裝）見
[三種取用方式](/start/three-ways)；上線之後怎麼跟進規範，見
[跟上新版](/governance/staying-current)。

## 收錄門檻

頁型跟元件過同樣的[三關](/)：去領域化、通用性、三次法則。
收錄前先檢查：換一個領域，這一頁的區塊順序與規則還成立嗎？只有某個業務流程需要的複合畫面，不收。

## 缺件與後續

組這五種頁會遇到的缺口如下。**先用替代方案，不要自己長一個私有版**；
需要正式元件時走 [RFC 流程](/governance/rfc)，過三次法則才收。
「認領」欄直達[缺件認領表單](https://github.com/kielchang/dooping-design-book/issues/new?template=missing-piece.yml)：
一則回報寫一個使用場景（＝三次法則的一次證據），湊齊三個場景即動工。
取用端的 agent 照 AGENTS.md「回饋到上游」開 issue（「類型」填缺件），入口見[回饋與 RFC 流程](/governance/rfc)；兩邊的證據由守門人合併計算。

| 缺件 | 目前替代 | 用在 | 認領 |
| --- | --- | --- | --- |
| Drawer | `Dialog`（行動版側欄抽屜已由 Sidebar 內建） | 各頁 | [提出](https://github.com/kielchang/dooping-design-book/issues/new?template=missing-piece.yml&piece=Drawer) |
| DefinitionList | 兩欄 grid 手排鍵值對 | 明細頁 | [提出](https://github.com/kielchang/dooping-design-book/issues/new?template=missing-piece.yml&piece=DefinitionList) |

（表單的下拉選項與這張表**逐字一致**；改表要同步改 `.github/ISSUE_TEMPLATE/missing-piece.yml`。）

已收錄、不再走替代方案的：
[Toast](/components/toast)、[Switch／Textarea／RadioGroup](/components/form-controls)、
[Skeleton](/components/skeleton)（規範正本在〈載入中〉，`DataTable` 內建 `loading`）、
[DateRange 期間選擇](/components/date-range)、
Form 包裝 → `FormField`／`FieldError`（見 [Input 的錯誤態](/components/input)）、
[Popover／DropdownMenu](/components/popover-dropdown)、Collapsible、Separator、[ConfirmDialog](/components/confirm-dialog)、
[PageHeader／Breadcrumb](/components/page-header)（含 `BackLink`）。

AppShell 與 Sidebar 以**純呈現元件**收在[元件章](/components/app-shell-sidebar)；站台層的規範正本在
[後台系統的資訊架構](/patterns/back-office-ia)。
