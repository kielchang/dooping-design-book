# 回饋與 RFC 流程

## 三種回饋，三條路

| 類型 | 路徑 | 期望回應 |
| --- | --- | --- |
| **Bug** | Issue，附最小重現 | 直接修 |
| **小調整**（文案、對比、一個 prop） | PR，附截圖或說明 | Review 後合併 |
| **新元件 / 新 token / 改語意** | **RFC** | 討論後決定 |

## RFC 要回答的五題

```markdown
## 問題
使用者遇到什麼？不解決會怎樣？

## 三次法則證據
這個東西在哪三個地方實際被需要過？（要有具體出處，不是「以後可能會用到」）

## 提案
API 長什麼樣？舉一個真實的使用情境。

## 替代方案
考慮過什麼？為什麼不採用？（沒有替代方案通常代表想得不夠）

## 影響
會不會改變既有行為？需要 major 嗎？現有使用者要做什麼？
```

## 三次法則

**只收實際用過三次以上且穩定的東西。**

<Rules>
  <Do><p>同一個問題在三個不同地方各自解決過一次 → 現在可以抽象了，
  而且你已經知道它的三種形狀。</p></Do>
  <Dont><p>不要在第一次遇到時就抽象。你只看過一種形狀，
  抽出來的介面九成會在第二次使用時被推翻——然後就變成一個沒人敢改的舊介面。</p></Dont>
</Rules>

三次法則的例外：**已知的無障礙或安全問題**。這種不必等三次。

## 誰決定

必須有**明確的守門人**（一個人或一個小組）。

沒有守門人的設計系統，三個月後會有五種按鈕——
每一種都是某次「這個 case 比較特殊」的產物，而且每一次都很合理。

守門人的工作不是說「不」，是問：
1. 三次法則過了嗎？
2. 拿掉領域脈絡還成立嗎？
3. 現有元件真的做不到嗎？

## 淘汰也要有流程

新增有流程，移除也要有：

1. 標記棄用（`@deprecated`，說明替代方案）
2. 保留至少一個 minor 版本
3. 下一個 major 移除

沒有淘汰流程的設計系統只會越長越胖，最後沒有人知道哪些還能用。
