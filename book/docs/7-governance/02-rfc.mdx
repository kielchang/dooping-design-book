# 回饋與 RFC 流程

## 入口

| 誰 | 送到哪 | 格式 |
| --- | --- | --- |
| **取用端的 agent** | GitHub issue，標題以 `[回饋]` 開頭 | [AGENTS.md](https://kielchang.github.io/dooping-design-book/AGENTS.md)「回饋到上游」——格式正本只有那一份 |
| **人** | 下一節的 GitHub 表單與 PR | 表單欄位 |
| **安全問題** | 私密回報，不開 issue | [SECURITY.md](https://github.com/kielchang/dooping-design-book/blob/main/SECURITY.md) |

取用端在**用的當下**就送，不必等自己湊滿三次；三次由守門人在上游數。判準（下面的五題、三次法則、守門人三問）一律相同。

## GitHub：三種回饋，三條路

| 類型 | 路徑 | 入口 | 期望回應 |
| --- | --- | --- | --- |
| **Bug** | Issue，附最小重現 | [Bug 回報表單](https://github.com/kielchang/dooping-design-book/issues/new?template=bug.yml) | 直接修 |
| **小調整**（文案、對比、一個 prop） | PR 開到 `dev`，附截圖或說明 | [開 PR](https://github.com/kielchang/dooping-design-book/compare/dev...)（模板自帶自查清單） | Review 後合併進 dev |
| **新元件 / 新 token / 改語意** | **RFC** | [RFC 提案表單](https://github.com/kielchang/dooping-design-book/issues/new?template=rfc.yml) | 討論後決定 |

另有一個入口：[**缺件認領表單**](https://github.com/kielchang/dooping-design-book/issues/new?template=missing-piece.yml)。
[頁面章缺件表](/pages/overview)的項目，回報一個使用場景＝三次法則的一次證據，
證據齊了由守門人升級成 RFC 或直接動工。拿不準走哪條路，先開缺件認領。

## RFC 要回答的五題

```markdown
## 問題
使用者遇到什麼？不解決會怎樣？

## 三次法則證據
這個東西在哪三個地方實際被需要過？（要有具體出處，不是「以後可能會用到」）

## 提案
API 長什麼樣？舉一個真實的使用情境。

## 替代方案
考慮過什麼？為什麼不採用？（沒有替代方案通常代表想得不夠）

## 影響
會不會改變既有行為？需要 major 嗎？現有使用者要做什麼？
```

正式提案直接用 [RFC 表單](https://github.com/kielchang/dooping-design-book/issues/new?template=rfc.yml)，
欄位與這五題一對一、逐欄必填。[符合性台帳](/governance/conformance-ledger)的四題
（問題、建議、影響範圍、如果不改會怎樣）是它的**下游速記版**：
在自己 repo 的台帳裡記錄用四題；取用端 agent 的回饋，骨架後四段就是這四題，三次證據由守門人在上游串起來；
人送正式提案用表單五題。

## 三次法則

**只收實際用過三次以上且穩定的東西。**

<Rules>
  <Do><p>同一個問題在三個不同地方各自解決過一次 → 這時才抽象。</p></Do>
  <Dont><p>不要在第一次遇到時就抽象。</p></Dont>
</Rules>

三次法則的例外：**已知的無障礙或安全問題**，不必等三次。

**三次由守門人在上游數，不是由單一取用端數。** 取用端每遇到一次就送一則回饋，串連是守門人的事（見下方「送出之後」）。

## 誰決定

必須有**明確的守門人**（一個人或一個小組）。

守門人問三題：
1. 三次法則過了嗎？
2. 拿掉領域脈絡還成立嗎？
3. 現有元件真的做不到嗎？

**本 repo 的守門人：[@kielchang](https://github.com/kielchang)**（`.github/CODEOWNERS` 宣告；
核准版的閘門——staging → main 的合併——由 ruleset 與 PR 上的核准清單強制，見 [ARCHITECTURE.md「分支與部署拓樸」](https://github.com/kielchang/dooping-design-book/blob/main/ARCHITECTURE.md#分支與部署拓樸)）。
token 與基礎章與其他部分同一位守門人；有第二位維護者之前不分開設。

## 提案的狀態機

RFC 的狀態用 label 表達，**狀態轉移只有守門人動手**：

| label | 誰掛 | 語意 |
| --- | --- | --- |
| `rfc` | 表單自動 | 類型標記，永不移除 |
| `rfc:討論中` | 表單自動 | 開立即此態，任何人可討論 |
| `rfc:已接受` | 守門人 | 三問通過，排進實作；實作 PR 合併時關閉 issue |
| `rfc:已婉拒` | 守門人 | issue 留一句**可被推翻**的理由後關閉（「因 X 不收，待 Y 成立可重提」） |
| `rfc:已擱置` | 守門人 | 通常是三次證據未滿；用缺件認領湊證據，齊了改回討論中 |

所有擱置中的提案：
[依 label 過濾](https://github.com/kielchang/dooping-design-book/issues?q=is%3Aissue+label%3A%22rfc%3A%E5%B7%B2%E6%93%B1%E7%BD%AE%22)，
不另維護清單。

## 送出之後

取用端回饋（標題 `[回饋]` 的 issue）與 RFC 用同一套 label 表達狀態，**轉移只有守門人動手**，送件方送出後不改標題、label 或狀態。

- **分流**：守門人每次切候選版之前，處理新進的 `[回饋]` issue。同對象的回饋在 issue 留言 `同類：#a #b` 串起來，湊滿三則就往下走。
- **不等三次**：確認是不符規範就直接修；無障礙問題收到即處理；安全問題走 SECURITY.md 私密回報。
- **採納**：小調整直接修；新元件／新 token／改語意轉成 RFC。實作 PR 合併時關閉 issue，變更寫進 CHANGELOG。
- **婉拒**：issue 留一句可被推翻的條件後關閉（「因 X 不收，待 Y 成立可重提」），不刪。下一則同類進來時，先重讀上一則的結論。

本站不設 RFC 檔案庫、也不放決策紀錄：規則寫在守衛與各章那一句。

## 淘汰流程

1. 標記棄用（`@deprecated`，說明替代方案）
2. 保留至少一個 minor 版本
3. 下一個 major 移除
