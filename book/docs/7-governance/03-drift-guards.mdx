# 漂移防護

## 三道防線

同一條規則可以擋在三個地方：

| 防線 | 手段 | 擋掉什麼 |
| --- | --- | --- |
| **① 編譯層** | 清空 Tailwind 預設色盤 | `bg-red-500` **產不出樣式** |
| **② lint** | ESLint 規則 | 繞過編譯層的逃逸路徑：`bg-[#fff]`、inline style 硬編色、深入內部路徑 |
| **③ 測試** | 守衛測試 | 結構性規則：相依邊界、token 成對、產物同步 |

:::tip 前兩道保護「取用端」，第三道保護「規範本身」
**三道要一起上。**
:::

### ① 編譯層：讓違規寫不出來

`@dooping/tokens` 的兩個 Tailwind 出口都**清空**預設色盤，套用之後 Tailwind 的預設色盤整個消失：

```css title="Tailwind v4：@dooping/tokens/tailwind.css 裡的這一行"
@theme inline reference {
  --color-*: initial;
  /* …其後才是語意色對映… */
}
```

```js title="Tailwind v3：preset 覆蓋（而非 extend）theme.colors"
module.exports = {
  presets: [require("@dooping/tokens/tailwind-preset")],
  content: ["./src/**/*.{ts,tsx}"],
};
```

```jsx
<div className="bg-red-500" />   {/* ❌ 產不出樣式，畫面上直接看得出來 */}
<div className="bg-danger-subtle" /> {/* ✅ */}
```

保留 `transparent`／`current`／`inherit`／`white`／`black`。
真的需要額外色階，在自己的設定裡**明示**加回去：Tailwind v4 在全域 CSS 用 `@theme { --color-<名稱>: …; }`，
v3 用 `theme.extend.colors`。不要改回預設色盤。

### ② lint：堵住繞路

**繞路**（`bg-[#ff0000]`、`style={{ color: '#f00' }}`、
直接 import 上游內部路徑）用 ESLint 擋：

```bash
# 複製到你的專案（跟元件一樣走複製，不是 npm 套件）
curl -O https://raw.githubusercontent.com/kielchang/dooping-design-book/main/templates/eslint.dooping.cjs
```

```js title=".eslintrc.cjs"
module.exports = { extends: ["./eslint.dooping.cjs"] };
```

讀過再用；`overrides` 那段依你的專案結構調整。

## ③ 把結構性規則寫成測試

以下八支都可以直接抄；各支在本 repo 跑不跑：

| | 守衛 | 在本 repo |
| --- | --- | --- |
| 1–4 | 邊界／barrel／token 一致性／詞彙 | ✅ 在跑 |
| 5 | 禁止原始調色盤字面色 | 建議；本 repo 只做了防線 ①（清空預設色盤） |
| 6 | Token 副本同步 | 不適用：本 repo 直接 alias 到產物，沒有副本 |
| 7 | 文件掛鉤 | ✅ 在跑（`tests/doc-hooks.test.ts`） |
| 8 | 雙站部署的路徑過濾 | 不適用：本 repo 的文件站與元件同一條管線、每次整站重建；三段部署各自一組 concurrency group |

第 6 與第 8 支寫給**有獨立文件站的宿主專案**。

規則的標示只有五種，全書統一：**✅ 在跑**（有會失敗的守衛）、**部分**（守衛只蓋到一部分）、**建議**（沒有守衛，取用端自行決定）、
**不適用**、**人工：由誰、何時**（沒有守衛，明說誰在什麼時點檢查）。沒有守衛的規則不得寫成「✅」，
只能標建議或人工。本 repo 全部守衛各管什麼、不管什麼，見
[ARCHITECTURE.md](https://github.com/kielchang/dooping-design-book/blob/main/ARCHITECTURE.md) 的守衛台帳。

### 1. 邊界守衛：元件不得依賴應用層

```ts
const ALLOWED_EXTERNAL = ["react", "react-dom", "@radix-ui/", "lucide-react",
                          "clsx", "tailwind-merge", "class-variance-authority", "@dooping/tokens"];

const FORBIDDEN = [
  { re: /from\s+["']zustand/,        why: "狀態管理屬於應用層" },
  { re: /from\s+["']react-router/,   why: "路由屬於應用層" },
  { re: /from\s+["']@\//,            why: "@/ 別名指向宿主專案" },
];

for (const file of shippedFiles) {
  for (const spec of imports(file)) {
    if (spec.startsWith(".")) continue;
    expect(ALLOWED_EXTERNAL.some((p) => spec.startsWith(p))).toBe(true);
  }
}
```

### 2. Barrel 覆蓋率：新元件不會被漏掉

```ts
const missing = shippedFiles
  .map(toModuleName)
  .filter((m) => !barrelSource.includes(`"./${m}"`));
expect(missing).toEqual([]);
```

Barrel 有兩個方向，守衛只擋其中一個：

- **漏掉**（守衛已擋）：新元件沒進 barrel
- **多出來**（守衛擋不住）：不該公開的東西進了 barrel

多出來的那一邊照下面的判準：**這個東西有沒有做出視覺或互動的決策？**

| 進 barrel | 不進 barrel |
| --- | --- |
| 有視覺／互動決策、任何專案都能用 | 綁定特定業務語彙（欄位名、狀態機、流程） |
| 只依賴 token 與彼此 | 需要應用層的狀態、路由、資料來源 |
| 有 story、有文件頁 | 只是把幾個元件拼在一起的私有便利函式 |

<Rules>
  <Do><p>拿不定主意就<strong>先不匯出</strong>。加進 barrel 是 minor，拿掉是 major。</p></Do>
  <Dont><p>不要為了「反正遲早會用到」預先匯出。</p></Dont>
</Rules>

### 3. Token 一致性：淺深成對、CSS 與來源同步

```ts
// 最容易發生的漂移：加了淺色 token 忘了配深色
const light = Object.keys(semanticColors("light"));
const dark  = new Set(Object.keys(semanticColors("dark")));
expect(light.filter((k) => !dark.has(k))).toEqual([]);

// CSS 產物與來源同步（防止有人手改 dist）
expect(missingInCss).toEqual([]);
```

### 4. 詞彙守衛：防止領域語意回流

```ts
const FORBIDDEN_TERMS = ["…產業術語…", "…角色流程詞…"];
// 掃描 packages/、book/docs、.github、registry
expect(hits).toEqual([]);
```

本 repo 的這一支確保示範資料與文件裡一個領域詞都不留。取用端依專案需要採用。

### 5. 禁止原始調色盤字面色

```ts
// 元件庫不得出現原始調色盤字面色，狀態色一律走語意 token
const FORBIDDEN_PALETTE =
  /\b(?:border|bg|text|ring|from|to|via|fill|stroke)-(?:amber|emerald|rose|sky|orange|yellow)-\d{2,3}\b/g;

for (const file of shippedFiles) {
  const hits = [...readFileSync(file, "utf8").matchAll(FORBIDDEN_PALETTE)];
  expect(hits, `${file} 請改用語意 token（如 text-success / border-edit）`).toEqual([]);
}
```

這支補防線 ① 與第 3 支擋不到的情況：

- 清空預設色盤之後，`bg-amber-500` **靜默產不出樣式**，不報錯。
- 取用端沒套 preset 時（[token 是唯一硬相依](/start/three-ways)），`bg-amber-500` 會**照常渲染成琥珀色**，不跟主題走。
- token 一致性守衛（第 3 支）**檢查不到沒用 token 的那一行**。

**特別要盯琥珀**：`--edit` 是保留色（見[提醒色辭典](/foundations/alert-colors)），不得用原始色階另寫琥珀色的高亮。

### 6. Token 副本同步

文件站能直接吃 token 產物（`@import` 或 alias）就不留副本（本 repo 的做法見下方「加分」一節）。
做不到時（文件站是另一個框架，直接匯入會與站台主題或深色開關衝突），留一份副本，並同時配一支守衛：

```ts
it("token 副本涵蓋樣式設定引用的全部變數", () => {
  const config = read("tailwind.config.js");
  const copy   = read("docs-site/src/css/tokens.css");

  const wanted = new Set(
    [...config.matchAll(/var\((--[a-z0-9-]+)\)/g)].map((m) => m[1])
      // 執行期由第三方元件注入的變數不是設計 token，不需入副本
      .filter((v) => !v.startsWith("--radix"))
  );
  expect(wanted.size).toBeGreaterThan(10);        // 守衛本身沒有空轉
  for (const v of wanted) expect(copy).toContain(`${v}:`);
});
```

Tailwind v4 宿主沒有 `tailwind.config.js`：把第一行換成讀全域 CSS——
`@theme` 區塊裡的 `var(--…)` 就是「樣式設定實際引用的變數」，其餘照舊。

| 重點 |
| --- |
| 以**樣式設定實際引用的變數**為準，不以來源檔的變數清單為準 |
| **排除執行期注入的變數**（第三方元件在 runtime 注入的 `--*` 變數不是設計 token） |
| 斷言「想要的集合不是空的」 |

<Rules>
  <Do><p>副本檔開頭寫清楚<strong>它是副本、來源在哪、由哪支守衛盯著</strong>。</p></Do>
  <Dont><p>不要以為「反正加 token 的時候會記得同步」。</p></Dont>
</Rules>

### 7. 文件掛鉤：引用的東西必須存在

文件嵌入真元件（story、示意流程、範例畫面）時，對元件庫的相依是**以字串為鍵**，每一個鍵都要驗證存在：

```ts
// story id 由 stories 檔的 meta.title + export 名推導（沿用 Storybook 的 id 規則）
const validIds = collectStoryIds("packages/react/src/**/*.stories.tsx");
for (const f of docFiles)
  for (const [, id] of read(f).matchAll(/<StoryFrame[^>]*id="([^"]+)"/g))
    expect(validIds.has(id), `${f} 引用不存在的 story：${id}`).toBe(true);
```

**失敗訊息要指出是哪個檔案引用了哪個不存在的鍵。**

順帶做兩件事：**禁止回歸**（把已經廢除的做法寫成斷言，例如「不要再用截圖」）、
**正向下限**（斷言文件至少嵌了 N 個視覺輔助）。

本 repo 這一支是 `tests/doc-hooks.test.ts`（嵌入的做法見
[零截圖文件示意](/patterns/zero-screenshot-docs#互動示意什麼時候該嵌-storybook)）。實作的兩條規則：

**一、id 的推導必須對著真值驗一次。** 拿 `build-storybook` 產物的 `index.json`
與「`meta.title` ＋ export 名」重算出的 id 逐一對照，雙向全中。**只跑「測試綠了」不算驗過。**

**二、行內程式碼要排除，圍籬程式碼要照驗。**

### 8. 雙站部署的路徑過濾與它的例外

應用程式與文件站各自獨立部署時，用路徑過濾：

```yaml
# 應用程式：文件變更不重佈
paths-ignore:
  - "docs-site/**"

# 文件站：文件變更才重佈……
paths:
  - "docs-site/**"
  # ……但元件變更也必須重佈（例外，見下）
  - "packages/react/**"
  - ".storybook/**"
```

<Callout variant="warning" title="容易漏掉的例外">
  **文件站內嵌元件與 story 時，元件變更必須觸發文件站重佈。**
  不要只設 `paths: ["docs-site/**"]`。
</Callout>

「零截圖」的承諾（元件改版，示意圖自動跟上）**必須寫進 CI 設定**。

好幾個部署寫入**同一個發佈分支的不同子目錄**時（本書是正式站、`preview/`、`staging/` 三段）：
**每段一組 concurrency group**，不要全部共用一組；
部署腳本只准動自己的目錄，push 被拒時重抓分支、重套自己的目錄、再推（`scripts/deploy-gh-pages.sh`）。

## 加分：讓文件站直接吃元件原始碼

```ts
resolve: { alias: { "@dooping/react": path.resolve("../packages/react/src") } }
```

文件裡的範例用**真元件**，不用複製品、不用截圖。

## 判準：什麼時候需要一支新守衛

<Callout variant="info" title="判準">
  **同一份事實只要存在於兩個地方，就需要一支守衛。**
</Callout>

| 兩個地方 | 守衛 |
| --- | --- |
| 淺色 token ↔ 深色 token | 成對檢查（第 3 支） |
| 元件檔 ↔ barrel | 覆蓋率（第 2 支） |
| token 來源 ↔ 文件站副本 | 副本涵蓋率（第 6 支） |
| 元件庫 ↔ 文件引用的 story id | 掛鉤存在性（第 7 支） |
| 元件庫 ↔ 已部署的文件站 | CI 路徑過濾（第 8 支） |

優先**讓那份事實只存在一個地方**：能 alias 就不要複製，能自動推導就不要手寫清單。
守衛用在消不掉的第二份上。
