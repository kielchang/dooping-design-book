# 符合性台帳

**適用**：打算持續跟上游升級的宿主專案。只抄一次就分家的專案不需要台帳。

## 一份台帳，三種狀態

每一個本地元件在台帳上有**一列**，狀態只有三種：

| 狀態 | 意思 | 後續動作 |
| --- | --- | --- |
| **遵循** | 對齊上游同名項目的規範與行為 | 上游 bump 時評估跟進 |
| **自製** | 上游沒有，本專案自行設計 | 具通用性 → 同時回饋上游（三次法則由上游數） |
| **刻意偏離** | 上游有，但本專案做法不同 | **必須寫原因**，同時回饋上游 |

<Callout variant="info" title="核心規則">
  **刻意偏離必須寫原因。沒寫原因的偏離不是偏離，是待修項目。**
</Callout>

原因在偏離**當下**寫。

<Rules>
  <Do><p>原因要寫成<strong>可以被推翻的形式</strong>：「上游只收 A，本地因為 B 而保留 C，
  待 D 完成後移除」。</p></Do>
  <Dont><p>不要寫「配合現有架構」。</p></Dont>
</Rules>

**不屬於設計系統範圍的東西不要進台帳**（綁定業務領域、依賴狀態管理或路由的元件）。
在台帳最後開一節列出來、註明「不需要對齊」。

台帳保持**短**：一張表，一列一個元件，狀態一個詞，備註一句話。

## 唯讀鐵律：下游不寫上游

上游與下游是兩個獨立的 repo，關係是**單向的**：

```
上游 ──讀──→ 下游        （隨時，拉下來自己評估）
上游 ←─回饋─ 下游        （送回饋或 PR，不是直接寫）
```

沒有 submodule、沒有共用工作區、沒有自動同步。

建議把唯讀做成**環境事實**，不只是規範：下游的環境對上游沒有寫入權限。

## 先在宿主做，同時回饋上游

發現上游規範有問題（缺一種狀態、規則不合用、有更好的做法）時：

```
在下游發現問題
   → 先在自己的宿主做出來，台帳記成「自製」或「刻意偏離」並寫明原因
   → 同一時間送一則回饋到上游（問題、建議、影響範圍、如果不改會怎樣）
   → 守門人跨系統數證據；三次法則過了排進計畫
   → 上游收錄並進版
   → 重抄上游版本，台帳該列改回「遵循」
```

括號裡的四題是 [RFC 五題](/governance/rfc)的**速記版**：台帳那一列寫一次，回饋照抄。
取用端 agent 的送件格式正本是 [AGENTS.md](https://kielchang.github.io/dooping-design-book/AGENTS.md)「回饋到上游」（開 GitHub issue）；
人走 GitHub 表單或直接開 PR；入口都列在[回饋與 RFC 流程](/governance/rfc)。

**順序：先做、記台帳，同時回饋；三次由上游數。**

上游不替任何子系統排程，也不收投機性抽象；宿主不等上游合併才動工。
收錄之後重抄、改回「遵循」，用 diff 看上游改了哪裡。

<Rules>
  <Do><p>急著上線就直接做，<strong>記成「自製」或「刻意偏離」並寫明原因</strong>，
  同時送一則回饋到上游。收錄之後重抄、改成「遵循」。</p></Do>
  <Dont><p>不要做了卻不記台帳。</p></Dont>
</Rules>

## 兩本帳，分工不重疊

宿主專案留**兩份**紀錄：

| 帳本 | 回答 | 讀者 |
| --- | --- | --- |
| **CHANGELOG** | 我的元件庫這次改了什麼 | 用這個元件庫的人（含未來的自己） |
| **符合性台帳** | 我跟上游的關係是什麼 | 要決定「上游 bump 了，我跟不跟」的人 |

CHANGELOG 是**時間序**（一直長），台帳是**現況快照**（維持同樣長度），兩者不混在一起。

一次變更常常兩本都要動：改了元件 → CHANGELOG 加一則；
如果這次改動讓某個元件從「刻意偏離」變回「遵循」→ 台帳那一列也要改。

## 上游更新不自動套用

怎麼知道上游 bump 了：**Watch 上游 repo 的 Releases**（每次進版自動發，
notes 就是 CHANGELOG 那一則；完整訊號表見[跟上新版](/governance/staying-current)）。
訊號送上門之後，動作是：

```
拉取 → 對台帳逐列評估 → 決定跟不跟 → 更新台帳的上游版本欄
```

不要 `npm update` 之後看 CI 綠不綠就算數。

**只評估標「遵循」的列。** 標「自製」的不受影響；標「刻意偏離」的重讀一次原因，
原因已經不成立（例如上游這次的改動正好解掉了它），那一列就收回來。

## 離線摘要：帶著關鍵規範走

宿主專案在自己的 repo 裡留一份**離線摘要**：色彩語意的四組 token、
模式的一句話版本與反例、無障礙的門檻值。不是完整複製，是**最常用的判斷依據**。
（相關：[漂移防護](/governance/drift-guards)。）

<Rules>
  <Do><p>摘要要<strong>明講它是摘要</strong>，並附上「完整內容請讀上游」與取得方式。</p></Do>
  <Dont><p>不要把摘要寫成第二份規範：摘要裡不出現上游沒有的規則。</p></Dont>
</Rules>

順帶把**取用方式的環境限制**也寫進摘要：哪條路通、哪條路不通
（文件站被公司 proxy 擋、API token 的授權範圍只涵蓋自己的 repo…）。
