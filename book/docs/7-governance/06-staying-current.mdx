# 跟上新版

導入之後的三件事：怎麼知道上游動了、怎麼判斷要不要跟、決定跟進之後每一層怎麼跟。
（導入本身見[導入三階段](/governance/adoption)；版號的定義見[版本策略](/governance/versioning)。）

## 訊號從哪來

上游進版時會發出的訊號如下。**至少訂閱一條，不要靠想起來**：

| 通道 | 涵蓋 | 怎麼訂 |
| --- | --- | --- |
| GitHub Release（`vX.Y.Z`） | 規範版：元件與 token 有取用端可感知的變更；notes 末尾列出**這一版動到的 registry item** | repo 頁 Watch → Custom → Releases，有新版就收到通知 |
| [CHANGELOG](https://github.com/kielchang/dooping-design-book/blob/main/CHANGELOG.md) | 每次進版一則，含「我需要做什麼」 | 判斷時讀；不適合當提醒機制 |
| `npm outdated @dooping/tokens` | token 層 | 放進宿主 CI 例行跑 |
| `dooping-check` | 元件層：**你抄過的 item**（含相依）上游動了沒、本地改了沒 | 下面的「例行檢查」，放進宿主 CI |
| `/r/index.json` | 機器可讀正本：規範 `version`、配對的 `tokensVersion`、每個 item 的指紋 `meta.closureHash` | 自己寫檢查時讀 |

要知道的四件事：

- **純文件進版不打 tag、不發 Release。** 沒有收到通知＝不需要任何動作。
- 規範版與 token 版是**配對**的：每版規範恰好宣告一個 tokens 版，
  正本在 `/r/index.json` 的 `tokensVersion`（見[版本策略](/governance/versioning)的配對模型）。
- **Release 的 item 清單分四類**：內容有變、只因相依變了而受影響、新增、移除。
  「只因相依受影響」的 item 也要重抄（例：修正落在 `utils` 時，抄了 `data-table` 的人一樣要重抄）。
- **訊號只來自核准版（`main`）。** 想提前試下一版，可以在自己的分支從 `/staging/r/` 裝來回報問題；
  正式導入與例行檢查一律對 `/r/`（見[版本策略「只參照正式站（main）」](/governance/versioning)）。

### 例行檢查：dooping-check

提醒用，**不擋建置**。一次性準備：

```bash
npx shadcn@latest add https://kielchang.github.io/dooping-design-book/r/dooping-check.json   # 裝進 scripts/dooping-check.mjs
node scripts/dooping-check.mjs init data-table page-header   # 列出你「主動」裝過的 item，相依會自動算進去
```

之後每週在宿主 CI 跑一次：

```bash
node scripts/dooping-check.mjs
```

每個 item 回報三種狀態之一：

| 狀態 | 意思 | 下一步 |
| --- | --- | --- |
| 已是最新 | 上游的指紋與 lock 相同，本地檔案也沒改 | 不必動 |
| 上游有更新 | 這個 item 或它的相依在上游變了 | 照輸出的指令先 `--dry-run --diff` 看差異；決定跟進就重抄，再 `update <item>` |
| 本地改過 | 本地檔案的內容與 lock 記的不同 | 刻意偏離就記進[符合性台帳](/governance/conformance-ledger)；不是刻意的，重抄即可 |

`dooping-check` 本身也是 registry item：它有更新時，檢查會把它列成「上游有更新」。
想讓提醒擋 PR 就加 `--strict`（不建議當預設）。

`dooping.lock.json` 會跟著 PR 進來，工具因此不完全信任它：

- **來源不是正式站**（`/r/` 以外的網址或本機資料夾）時，報告第一行會提醒——取用端只參照正式站。
- **來源是本機資料夾**時不印 `shadcn add` 指令：只給名稱的指令會裝到 shadcn 預設來源的同名元件。用產生那個資料夾的流程重抄。
- 建議指令的參數一律加雙引號；名稱或網址含引號、`$`、`%`、空白這類字元時不印指令，先確認 lock 有沒有被改過。
- lock 裡的檔案路徑只讀專案內的：絕對路徑或含 `..` 的當成缺檔，回報「本地改過」。
- 印到 GitHub Actions 的提醒，名稱與錯誤訊息裡的 `%`、換行會先跳脫，不會被當成另一行 CI 指令。

### 指紋怎麼算

`/r/index.json` 每個 item 的 `meta` 有兩個指紋，`dooping-check` 與 Release 的異動清單都靠它們：

- **`hash`**：取用端抄走的東西。依序串接下列各行（以換行分隔），取 SHA-256 的前 16 個十六進位字元：
  `name <名稱>`、`type <型別>`、`deps <npm 相依，排序後以空白串接>`、`registryDeps <registry 相依的 item 名稱，排序後以空白串接>`，
  然後每個檔依 `target` 排序各一段 `file <target> <type> <內容長度>` 接內容。排序照字元碼位。
  **不含**版號、標題、說明與 URL：同一份內容在預覽站與正式站的指紋相同，只改說明文字不改指紋。
- **`closureHash`**：自己加上所有遞移 registry 相依的名稱，排序後每行 `<名稱>:<hash>`，再取 SHA-256 前 16 字元。
  **任何一個相依變了它就變**：`utils` 修了，`data-table` 的 `closureHash` 跟著變、`hash` 不變。

這套串接規則是對外契約。實作在 `scripts/lib/fingerprint.mjs`。

裝不了腳本的專案，改比對規範版號（粒度只到「規範動了」，看不出動到哪些 item）：

```bash
UPSTREAM=$(curl -s https://kielchang.github.io/dooping-design-book/r/index.json | jq -r .version)
RECORDED="0.10.0"   # 你的台帳記錄的上游版本，跟著台帳一起改
if [ "$UPSTREAM" != "$RECORDED" ]; then
  echo "::warning::上游規範已到 v${UPSTREAM}（台帳記 v${RECORDED}）——讀該版 CHANGELOG 決定要不要跟。"
fi
```

## 判斷要不要跟

<FlowStayingCurrent />

1. **讀該版 CHANGELOG 的「我需要做什麼」。** 寫不需要就結束。
2. **對照[符合性台帳](/governance/conformance-ledger)。** 只評估標「遵循」的列；
   「自製」不受影響，「刻意偏離」重讀一次原因。
3. **依影響決定**（版號差距只表示上游改了多大：大版差＝有會壞的變更、中版差＝有新能力、小版差＝修正微調）：

| 情況 | 決定 |
| --- | --- |
| 上游修了你也踩到的問題 | **跟進**，這是唯一「必須同步」的情況 |
| 有用的新能力，但這期排不進 | **記台帳、延後**——在台帳的上游版本欄記下差距 |
| 與本地的刻意做法衝突 | **偏離**，在台帳寫下原因（沒寫原因的偏離是待修項目） |

<Rules>
  <Do><p>把「上游 bump」當成一個要排程的<strong>決定</strong>：逐列評估、更新台帳、
  在自己的 CHANGELOG 記一則。</p></Do>
  <Dont><p>不要 <code>npm update</code> 之後看 CI 綠就當作升級完成。</p></Dont>
</Rules>

## 決定跟進之後：每層的程序

| 層 | 程序 |
| --- | --- |
| token | `npm update @dooping/tokens`（`^` 範圍內）。跨大版先讀 CHANGELOG；0.x 期間任何版本都可能 breaking，語意色**名稱**已穩定、值仍可能調 |
| 元件 | 重跑同名 `npx shadcn@latest add <URL>`（覆寫 `components/dooping/` 同名檔，相依會一起覆寫；先加 `--dry-run --diff` 看會動到哪些檔）→ 用 `git diff` 逐檔審查 → `node scripts/dooping-check.mjs update <item>` → 台帳該列更新上游版本 |
| 模式／頁面 | 重讀該則文件，對照本地實作；有差就記台帳（遵循／刻意偏離） |

<Rules>
  <Do><p>元件更新走「重抄＋diff 審查」，把上游的改動<strong>看過一遍</strong>再合進去；
  本地改過的部分逐塊決定保留或讓位。</p></Do>
  <Dont><p>不要手動把上游的改動「挑幾行抄過來」。</p></Dont>
</Rules>

## 開發中的節奏

1. **新畫面動工前先查上游**：到[頁面章](/pages)選頁型、查元件章有沒有現成件。
2. **缺件不長私有版**：先用[缺件表](/pages/overview)的替代方案，同時把缺口回饋上游
   （入口與格式見[回饋與 RFC 流程](/governance/rfc)）。
3. **節奏掛在里程碑上**：sprint 或版本邊界檢查一次訊號。衝刺中收到新版訊號，記台帳延後——**衝刺中途不升大版**。
4. **台帳與[離線摘要](/governance/conformance-ledger)跟著改。**

<Rules>
  <Do><p>把「檢查上游」寫進里程碑的定型工作（跟「更新相依」同一個時段做）。</p></Do>
  <Dont><p>不要等到「畫面看起來怪怪的」才發現落後。</p></Dont>
</Rules>
