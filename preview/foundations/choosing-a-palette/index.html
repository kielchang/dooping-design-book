色票配色策略

適用：換品牌色、新增色相主題、新增或重生分類色票、調整任何生成出來的色值時。 已定案的值見色彩語意、深淺主題、提醒色辭典； 圖表上每個系列取哪一種顏色，見圖表的配色策略。

不能靠目測，要靠驗證器。 值由生成器產生，由 npm run verify:color 驗收。

三層：語意 → 色相預算 → 並存​

配色分三層，由上而下套用：

層規則詳見
1. 語意Token 名稱說「代表什麼」；語意色是唯一的色彩 API，色階不外露。狀態色語意固定，切主題、切深淺都不變色彩語意、提醒色辭典
2. 色相預算主題色相只進識別層（帶色調中性色、--brand 家族）；動作、互動、聚焦環、狀態色、圖表色都不吃主題色相深淺主題 → 色相預算
3. 狀態色與主題色並存色相：警報色域保留，有彩度的 brand 距所有狀態色 ≥ 25°。飽和度：--danger 是畫面上最飽和的色。面積：高飽和色（提醒關鍵色＋圖表重點色）共用 10%色彩語意 → 並存三層

分類色票（--chart-1 … --chart-8）不進這三層：與狀態語意脫鉤、不跟主題走、不得靠近任何狀態色， 見色彩語意 → 分類色票。

值是生成的，不是挑的​

主題色、帶色調中性色、提醒淡底、側欄表面、分類色票，以及未達標的狀態色前景，都由 packages/tokens/scripts/generate-theme.mjs 生成：給定目標（對比比值或感知距離），反解明度與彩度。

npm run build:theme    # 重新生成主題色、淡底、圖表色票（改寫 tokens.json）
npm run build:tokens   # 由 tokens.json 重產 tokens.css、tailwind.css、tokens.data.ts
npm run verify:color   # 閘門：有不合格項就 exit 1
生成的值做法參數
--brand／--brand-foreground固定色相與彩度上限，反解明度使白字達 4.5:1，取最亮的解；無品牌色的主題鏡射 --primaryTHEMES 的 hue、cap、neutralBrand；深色彩度 × DARK_CHROMA_FACTOR
--brand-subtle／-foreground淺色從最淡往深探、深色從最深往亮探，取第一個與該主題 --muted、--sidebar 都拉開 ΔE00 8 的值；文字反解到 4.5:1SUBTLE_MIN
14 個帶色調中性色只轉色相，明度與彩度不動；--muted-foreground 對該主題的 --muted 反解到 4.5:1NEUTRAL_TINT
狀態色前景未達 4.5:1 才修：success／warning／info 改同色相深墨前景；danger／destructive 保留白字、壓深填色—
--{狀態}-subtle／-foreground四種共用一個明度，各色相彩度反解到同一個染色量；文字反解到 4.5:1SUBTLE_TINT、SUBTLE_L_BAND
--sidebar反解到與頁面底的目標 ΔE00SIDEBAR_TINT
--chart-1 … --chart-8從候選池以最遠點插入挑出（見〈排序：最遠點插入〉）CHART_BAND、CHART_CHROMA、HUE_SPACING、ANCHOR_HUE

一律取整成 8-bit 之後再驗，對實際的前景與表面 token 驗（見色彩語意 → 對比要求）。

✅ 這樣做

要改值就改生成器參數，重跑 npm run build:theme。

🚫 不要這樣

不要手改 tokens.json 裡生成出來的值。

驗證門檻​

所有門檻都對六組主題 × 淺深兩模式驗；守衛欄寫由誰擋。 verify:color 的不合格項同時讓 npm test 紅（tests/color.test.ts 跑同一組檢查）；warn 不擋，總數超過 15 則 npm test 紅。

新增門檻要反向驗證：暫時把值改回壞的，確認那一條真的會紅。

✅ 這樣做

用真正的頁面背景值驗（卡片底色、表格底色）， 不是白色與純黑。這與無障礙四原則第 3 條是同一條規則。

🚫 不要這樣

不要用色票研究時的比較底色驗完就收工。

✅ 這樣做

驗證器的結果連同 warn 一起留下，並註明 warn 的補償措施 （例如「這一色只能搭配標籤或明細表使用」）。

🚫 不要這樣

不要把 warn 當成 pass：warn 的色不能單獨承載訊息。

淺深各一組，各自驗​

淺深各一組獨立的值，各自驗證。「每個模式各一份報告」是覆蓋要求，不是格式要求。

覆蓋範圍要逐字等於宣稱的保證​

分類色不得撞語意狀態色；比對對象是全部六個狀態色，不是只比 danger。 只驗一個對象，等於沒有驗那一類。

驗感知量，不驗參數值​

驗證器要驗的是感知量，不是參數值。 例：四個狀態淡底以染色量等量，不以彩度數值相等。

背景改版之後，驗證結果全部作廢​

只要動過背景色（深色模式重做表面層次、卡片底色調亮一階）， 所有色票的驗證結果都必須重跑：先 npm run build:theme 重新生成，再 npm run verify:color。

驗證結果旁邊記背景值

把驗證所用的背景值記在結果旁邊，並在背景 token 變更的檢查清單裡 加一條「重跑色票驗證」。

門檻優先序​

門檻的優先序

無障礙門檻（對比、色覺障礙 ΔE00）不得為了美感放寬； 擠不下去時放寬的是美感約束（明度帶、彩度上下限、色相間距）。

約束項目擠不下時
無障礙門檻對比 4.5:1／3:1、分類色兩兩 ΔE00 ≥ 10（含 protan／deutan）不放寬
美感約束明度帶 CHART_BAND、彩度上下限 CHART_CHROMA、色相間距 HUE_SPACING先放寬這裡

加一條硬約束（例如「不得靠近狀態色」）的同時，放寬一條美感約束 （色相間距、明度帶上下限）。

先過驗證，再談風格。

排序：最遠點插入​

分類色票的順序就是安全順序：

  1. 第 1 色錨在藍（ANCHOR_HUE）：候選池裡色相最接近錨點、明度最接近明度帶中點的那一個。
  2. 之後每一色：在與已選各色色相差 ≥ HUE_SPACING 的候選裡，取「與已選色的最小感知距離最大」的那一個。 感知距離取一般、protan、deutan 三種視覺下 ΔE00 的最小值。
  3. 取用端照序取 --chart-1 … --chart-k，不重排、不循環。

候選池＝明度帶內 × 每 2° 一個色相，彩度落在上下限內、對頁面底 ≥ 3:1、且不靠近任何狀態色。 前 k 色的最差一對見色彩語意 → 順序即安全順序。

✅ 這樣做

PALETTE[0] 要穩定：它是單序列圖表沒指定顏色時的預設色。

🚫 不要這樣

不要用「取材來源的命名順序」或色相環順序當陣列順序。

定案​

定案＝只改 token 的值。換色票不動任何一行使用它的程式碼（見色彩語意的命名）。

例外：重新排序會打到寫死索引的畫面。 寫成 PALETTE[3] 的地方，重排之後對應到的是不同色相。

✅ 這樣做

重排色票時，把所有寫死索引的位置列出來逐一目視， 當成這次變更的驗收項目。

🚫 不要這樣

不要以為「反正只是換顏色」。

定案前依序完成：

  1. npm run build:theme，再 npm run build:tokens
  2. npm run verify:color 全過；warn 連同補償措施記下
  3. npm test
  4. 候選組（含淘汰組）與驗證結果留在文件或 story 裡
  5. token 值有變：依版本策略定 @dooping/tokens 的版號，CHANGELOG 寫一則

新增一組主題​

  1. 選色相：OKLCH 色相落在可用區間（109°–137°、188°–213°、264°–352°）， 且距六個狀態色都 ≥ 25°（見深淺主題 → 新增主題）。
  2. 加參數：在 packages/tokens/scripts/generate-theme.mjs 的 THEMES 加一筆（欄位見下表）。
  3. 生成：npm run build:theme，再 npm run build:tokens。
  4. 驗收：npm run verify:color。沒過或生成器丟錯（無解、拉不開），回第 1、2 步改參數重跑（見下表）。
  5. 改測試：tests/color.test.ts 的主題數斷言改成「主題數 × 2」，跑 npm test。
  6. 補文件：深淺主題的主題清單加一列。 Storybook 工具列與宿主的主題選單讀 tokens，不必另外登記。
  7. 定案：見〈定案〉。

THEMES 的欄位：

欄位填什麼
namedata-color-theme 的值
label顯示名
hue第 1 步選定的 OKLCH 色相
cap淺色的彩度上限，深色自動 × 0.75；現有有彩主題是 0.130–0.150
neutralBrand只有無品牌色的主題設 true（--brand 鏡射 --primary）

沒過時改哪個參數：

verify:color 報的改什麼
brand 色相距某狀態色不足 25°，或與最近狀態色 ΔE00 不足 12換 hue
brand 的 chroma 不低於 danger降 cap
brand 與停用外觀 ΔE00 不足 12加大 cap；沒有品牌色的主題改設 neutralBrand: true

新增或擴充分類色票​

新增：重生一組色票​

1. 一次做多組候選，並排比較。 至少做 5–7 組，每組給一個風格描述（「沉穩企業感」「高飽和儀表板感」「柔和親和」）， 用同一份資料、同樣幾張圖、淺深兩色模式並列呈現。

候選的來源可以是既有色票、品牌情緒板、公開的色票庫，但沒有一組能直接拿來用： 只取它們的方向（色相家族、飽和度層級），轉成生成參數 （CHART_BAND 明度帶、CHART_CHROMA 彩度上下限、HUE_SPACING 色相間距，淺深各一組）。

✅ 這樣做

把候選組與它們的驗證結果留在文件或 story 裡， 包含被淘汰的那幾組。

🚫 不要這樣

不要只做一組然後開會表決。

2. 每組各跑一次 npm run build:theme → npm run verify:color，每組候選、每個模式各一份報告。 在自己的技術棧驗證時，報告至少要有這些：

// 驗證器的輸出長這樣：每組候選、每個模式各一份
// { 亮度帶: pass, 彩度: pass, CVD分離: warn(ΔE 11.4 floor), 對比: pass }
//
// 三件事必須寫進報告，否則結果無法被重現：
//   1. 用哪個背景值驗的
//   2. ΔE 的地板值定在多少
//   3. 哪幾色只是「勉強過」（下次微調時第一個被動的就是它們）
for (const mode of ["light", "dark"]) {
  report[mode] = validate(palette[mode], { background: SURFACE[mode].bg, deltaEFloor: 10 });
}

3. 沒過：改參數，不改值。 依〈門檻優先序〉先放寬美感約束，無障礙門檻不動。

4. 選定：先過驗證，再談風格。

5. 定案：見〈定案〉；順序有變時，逐一目視寫死索引的畫面。

擴充：類別超過八個​

  1. 先合併：尾端類別併成「其他」，明細放在別處（capItems）； 跨圖表反覆出現的實體用 colorByKey，第 9 個以後退 --muted （見圖表的配色策略）。
  2. 仍要第 9 色：新增 token 走 RFC。通過後生成器、verify:color 與 PALETTE 的色數一起改，再照〈新增：重生一組色票〉第 2–5 步跑。
✅ 這樣做

八色不夠時，合併尾端類別成「其他」，並在別處提供明細。

🚫 不要這樣

不要「再加兩個顏色就好」。
