版本策略

三層各自獨立版號。

套件版號意義
@dooping/tokens契約。變動影響所有宿主
@dooping/react參考實作。使用者複製走之後就與版號脫鉤
文件站跟著 repo，不獨立發版

只參照正式站（main）​

版本網址能不能參照能不能安裝
核准版（main）正式站根目錄其他系統只參照這裡/r/、npm
候選版（staging）/staging/不能可以在自己的分支試裝回報，不可正式導入
預覽站（dev）/preview/不能不供安裝

進版＝核准版前進一次。 每一次進版對應 CHANGELOG 的一則。

只參照正式站

其他系統一律以 main 的正式網址為準。 /preview/ 與 /staging/ 都掛著不可關的橫幅，也不給搜尋引擎收錄。

每一段的 registry 都用自己的網址建置，相依指回同一段：從 /staging/r/ 裝，拿到的全部是候選版。 想提前試下一版，就在自己的分支從 /staging/r/ 裝，把問題回饋上游（入口見回饋與 RFC 流程）；正式導入一律用 /r/。

發佈流程（分支、驗收、核准）見 ARCHITECTURE.md「分支與部署拓樸」。

兩個對外訊號​

訊號給誰看什麼時候動
規範版號 vX.Y.Z（GitHub tag ＋ registry 戳記）所有取用端元件、token 或模式有取用端可感知的變更
@dooping/tokens 的 npm 版號有安裝 token 套件的系統token 內容變更

規範版號的大中小表示分量：大＝會壞、中＝有新東西、小＝修正微調（判準見下方兩張 SemVer 表， 對象是規範整體）。純文件進版不 bump、不打新 tag：沒有新版號＝取用端不需要任何動作。

版號正本是根目錄 package.json 的 version；packages/react 與 version.ts 跟隨它、 registry 戳記由它產生（守衛測試強制四處一致）。tag、戳記與 /r/index.json 的 version 是同一個號碼。

tag 只在核准版前進時蓋，版號可能跳號：dev 上累積好幾次 bump 才送出候選版時，只有最後那個版號有 tag。 每次進版發 GitHub Release（版號沒動就不發），訂閱方式與收到訊號後的判斷見跟上新版。

三層版號的對應關係（配對模型）​

規範與 tokens 兩條版號線不同步前進；哪一版規範配哪一版 token，不靠同號，靠宣告。

定義：每個規範版恰好宣告一個 tokens 版。樞紐是 packages/react/package.json 的 "@dooping/tokens": "x.y.z" 那一行， 它是配對的唯一正本，以下體現都從它產生：

體現處形式給誰用
/r/index.json 的 tokensVersion機器可讀配對（與 version 並列）取用端一個端點問到配對
registry item 的 dependencies@dooping/tokens@^x.y.znpx shadcn add 自動裝對
v* tag 的訊息「tokens 配對版：x.y.z」從 git 稽核，不翻 CHANGELOG
CHANGELOG 標題「規範 vA／tokens vB」要升級的人

多對一合法、一對多非法：token 沒變時，多個規範版指向同一 tokens 版 （例：v0.6.0 與 v0.6.1 都配 0.5.0）；一個規範版不得宣告兩個 tokens 版（守衛強制宣告是單一值）。

規範  v0.1.0  v0.2.0  v0.2.1   v0.4.0   v0.6.0  v0.6.1
        │       │       │        │        │       │
tokens 0.1.2 ──┴───────┘       0.3.0    0.5.0 ──┘

^ 決定配對的鬆緊：0.x 之下 ^0.6.0 ＝ >=0.6.0 <0.7.0。 同 minor 的 token 修補自動吃（不必重抄元件）；宣告跨了 minor，回 CHANGELOG 看要不要跟進。

取用端自查：

npm ls @dooping/tokens; curl -s https://kielchang.github.io/dooping-design-book/r/index.json | jq -r .tokensVersion

兩個數字的關係只有三種：相等＝配對正確；本地落後＝該升級 token； 線上 tokensVersion 比 npm 能裝到的還新＝上游合併了但還沒發佈（等，或提醒維護者）。

Token 的 SemVer 定義​

變更級別
移除或改名一個 tokenmajor
改變一個 token 的語意（--warning 從黃變紅）major
改變 --radius 之類會影響全站外觀的基準值major
新增 tokenminor
新增可 import 的入口檔（例：@dooping/tokens/tailwind.css）minor
微調色值但語意不變（對比修正）patch
修正 CSS 產物的 bugpatch

什麼不該發版​

以下變更不動 npm 版號：

變更npm 版號進 main
封裝設定（exports、files）的整理——不新增可 import 的入口不 bump✅
CI、建置腳本、測試不 bump✅
文件、註解、重構、改名不 bump✅

這些照樣進 main、文件站與 registry 照樣更新，等下次有 token 變更時一起發版。

✅ 這樣做

移除 token 前先標記棄用，保留至少一個 minor 版本， 並在 CHANGELOG 寫清楚替代方案。

🚫 不要這樣

不要「順手改名」token。

元件的 SemVer 定義​

變更級別
移除或改名 propmajor
改變預設行為（例如分頁預設值）major
新增 prop（有預設值）minor
新增元件minor
視覺微調、修 bugpatch

視覺變更也算變更（例：padding 從 8px 改成 12px）：至少 patch，並寫進 CHANGELOG。

元件的版號以戳記交付：每個 registry item 與 /r/index.json 都帶 version 欄位。 「我抄的是哪一版」看複製進來那份，「現在最新是哪一版」看線上 index：

curl -s https://kielchang.github.io/dooping-design-book/r/index.json | jq -r .version

CHANGELOG 寫給誰看​

寫給要升級的人。每一版的標題下一行寫一句對你的意義（含規範與 tokens 的版號變化）， 底下每一項回答：

  1. 改了什麼
  2. 我需要做什麼（不需要就明說「無須調整」）

文件版本對映產品版號​

這一節與下一節是給取用端系統的做法（設定頁、列印頁尾）。本書自己不做文件快照： 下一版看 /staging/，舊版看 git tag。

文件做版本快照，版號直接沿用產品版號。

版本內容標示
current（掛在 /next）開發中、尚未發佈未發佈橫幅，每頁常駐
最新快照＝正式環境現在跑的版本預設顯示
舊快照還有人在用的舊版版本下拉可切

三個實作細節：

  1. 預設顯示「最新快照」，不是 current。
  2. 未發佈的內容要有橫幅，而且要在每一頁。
  3. 設定要動態讀取已有的快照清單，不手寫版本清單。

發佈 SOP 要把快照綁進去：bump 版號 → 寫 CHANGELOG → 快照文件 → 合併發佈。 快照要跟在 bump 後面，成為同一個步驟。

✅ 這樣做

文件版號直接用產品版號，不要另起一套。

🚫 不要這樣

不要每次改錯字都快照一次。

產出物的身分（provenance）​

每一個離開系統的產出物，都要帶著自己的身分。

單一來源、建置時注入、三個地方顯示：

建置時注入：
  __APP_VERSION__ = package.json 的 version
  __GIT_SHA__     = CI 環境變數的 commit（取前 7 碼），本地建置＝ "dev"
  __BUILD_TIME__  = 建置當下時間

單一來源：
  version.ts 讀這三個常數，對外只匯出組好的字串與連結
顯示位置形式用途
側邊欄最底v1.4.2 · a3f9c21（可點開對應 commit）常駐，回報問題時看這裡
設定 →「關於」版號、commit 連結、建置時間、環境完整資訊
列印頁尾v1.4.2 · a3f9c21　2026-07-29 14:20 產生三處裡最優先，見下

列印頁尾​

形式見上表；做法見列印與匯出第 6 條。

本地建置要顯示 dev​

v1.4.2 · dev        ← 有人在自己機器上建的
v1.4.2 · a3f9c21    ← CI 建的，可追溯
✅ 這樣做

版號字串只有一個來源，側邊欄、關於頁、列印頁尾共用同一個匯出。

🚫 不要這樣

不要在列印頁尾另外寫一次版號。

✅ 這樣做

注入機制要防呆：常數沒被注入時（例如某個測試環境直接跑原始碼） 也不能讓畫面崩掉，退成 dev 即可。

🚫 不要這樣

不要讓「顯示版號」出錯時讓整個應用程式白屏。

元件版號放在元件庫裡​

元件版號標示抄的是哪一版，供日後對照上游的修正。 版號檔放在元件庫裡面（packages/react/src/version.ts），隨元件一起被複製走；不只放在 package.json。
